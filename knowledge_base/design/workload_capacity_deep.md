Workload and Capacity Planning — Deep Explanation

Core Reasoning Summary

Definition: Workload and capacity planning translates business scale into concrete application and database load assumptions such as requests per second, database operations, read/write mix, data growth, peak traffic, latency, and availability requirements.

Why it exists: User counts and labels such as "large application" do not directly determine database capacity. Architecture decisions need measurable workload assumptions.

When to use: Use workload and capacity analysis before making scaling decisions such as caching, replicas, partitioning, sharding, or capacity upgrades.

When NOT to use: Do not use registered-user count, application size, or a vague "high traffic" label as sufficient evidence for a specific database architecture.

Primary rule: Translate scale statements into workload numbers before selecting a scaling mechanism.

Advantages: Prevents premature scaling decisions and makes architectural assumptions explicit.

Disadvantages: Estimates are uncertain and require realistic traffic patterns, database-operation counts, growth assumptions, and peak behavior.

User count is not traffic

User-Count Boundary

Registered users are a scale descriptor, not a direct workload measurement.

A statement such as "10 million users" is insufficient to justify sharding, replicas, caching, or any other specific database architecture without translating it into active users, concurrency, request rates, database operations, and other workload assumptions.

Registered users, daily/monthly active users, concurrently-online users, and requests per second are all different quantities, and conflating them leads to wrong capacity assumptions. "10 million registered users" says very little on its own about database load.

Example capacity calculation

Estimation Boundary

The calculation provides a starting assumption, not a production capacity guarantee.

Real traffic depends on user behavior, request distribution, burstiness, caching, and the number of database operations generated by each request. Validate the assumption against representative workload data when available.

If 1,000,000 active users each generate roughly 10 requests per minute:

1,000,000 × 10 / 60 ≈ 166,667 requests/sec average

This is only a rough estimate — real traffic depends heavily on actual user behavior and request distribution, and should be treated as a starting assumption to state explicitly, not a precise prediction.

Important caveat — HTTP requests are not database operations

Request-to-Database Boundary

There is no fixed conversion between HTTP requests and database operations.

One application request may issue multiple database queries, no database query because of a cache hit, or a different number of operations depending on the code path.

Capacity analysis must therefore state explicitly whether a number refers to application requests or database operations.

One API call may execute multiple database queries, a cached response with zero queries, or a single query — there's no fixed ratio. Any workload estimate should distinguish "application-level traffic" from "actual database operations," and state which one a given number refers to.

Read vs write workload

Read/Write Boundary

A read-heavy or write-heavy label is a workload characteristic, not an automatic architecture choice.

Read-heavy workloads may benefit from caching, replicas, query/index optimization, or search projections depending on the actual bottleneck. Write-heavy workloads require analysis of write throughput, index maintenance, transaction contention, storage I/O, and replication overhead.

Read-heavy workload — retrieval dominates. Caching (caching.md), read replicas (replication_deep.md), query/index optimization (indexing_deep.md), and search projections (search_architecture.md) are the typical levers.

Write-heavy workload — inserts/updates dominate. Index maintenance cost, transaction duration, lock contention, storage write throughput, and replication overhead (replicating every write) become the important constraints.

A 90:10 read/write ratio means approximately 90% reads and 10% writes of the relevant operations. This split should inform which optimization levers are actually worth prioritizing.

Hot data and hotspots

Hotspot Boundary

Aggregate traffic can hide concentrated load.

A system that appears within average capacity can still fail when a small number of records or keys receive disproportionate traffic. Capacity analysis must consider traffic distribution, not only total RPS.

A small portion of records can receive a disproportionate share of traffic (a viral post, a popular event's seats). Hotspots can make caching strategy or data-distribution design more important than the raw total dataset size — a system correctly sized for average load can still buckle under a concentrated hot key. See "hot keys" in caching.md and "hotspot" in sharding_deep.md for concrete mitigation approaches.

Peak traffic

Peak-Capacity Boundary

Average traffic is insufficient for systems with bursty workloads.

The architecture should state the expected peak and how long the peak lasts, because a short spike and sustained peak can create different capacity requirements.

Ticket releases, flash sales, promotions, and batch jobs can create short traffic spikes far larger than average load. Any capacity plan should state the peak assumption explicitly and design for it — average-load sizing alone is a common and costly underestimate.

Data growth estimation

Growth Boundary

Data-growth estimates must include more than primary table rows.

Indexes, replicas, history/audit data, backups, and retention policies can materially increase storage requirements and should be included when sizing storage.

A rough estimate:

records/day × average row/document size × retention period

Then account for indexes (which add their own storage), replicas (each a full additional copy), audit/history data (see temporal_audit_data.md), and backups.

Design principle

Architecture-Selection Boundary

Workload numbers support architectural decisions only after the agent connects them to a specific bottleneck and requirement.

Even a high measured workload does not automatically imply sharding or replicas if the existing architecture still has sufficient capacity or a simpler optimization addresses the actual bottleneck.

"10 million users" is not, by itself, evidence for sharding, read replicas, or any specific architectural decision. The agent (and the reviewer) should translate a business-scale statement into concrete workload assumptions — RPS, read/write ratio, data growth, peak multiplier — before making architecture decisions based on it.

Common mistakes

Treating registered user count as if it directly implies request rate.

Sizing only for average load and ignoring realistic peak multipliers.

Confusing HTTP request rate with database operation rate.

Recommending sharding/read replicas/caching from a vague "it's a big app" impression rather than a stated workload estimate.

Ignoring hotspot risk because aggregate numbers look manageable.

Review questions

What specific numbers (RPS, read/write ratio, data growth, peak multiplier) support this architecture decision?
